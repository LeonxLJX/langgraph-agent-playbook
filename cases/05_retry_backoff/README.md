# 案例 05 · 上游限流退避重试（🟡 中级）

> 一句话：**上游 429 / 5xx / 超时，不要裸重试（会雪崩），要用指数退避 + 抖动。**

## 难点是什么
Agent 依赖的上游（LLM、业务服务、第三方）会限流、超时、抖动。直接无脑重试：
- 打得更狠，可能触发更严的限流，形成二次雪崩；
- 多个实例同时重试，形成“惊群效应”。

## 为什么会发生
很多人把重试写成 `for _ in range(3): try: ... except: time.sleep(1)`。固定间隔、无抖动、
且把所有异常都重试 —— 三个错误全踩。

## 生产级解法（看代码 `main.py`）
1. **只重试可恢复异常**：429 限流、5xx、超时、连接错可重试；4xx 业务错不重试。
2. **指数退避 + 抖动**（tenacity `wait_exponential_jitter`）：退避时间指数增长并加随机抖动，
   避免惊群。
3. **设最大尝试次数**，超限后 `reraise`，让上层守卫节点把错误转成可读消息（不崩图）。
4. 尊重上游 `Retry-After`（示例简化，生产请读响应头）。

## 调试清单
- [ ] 重试条件写对了吗？4xx 不该重试，重试只会放大失败。
- [ ] 有抖动吗？纯指数退避在并发场景也会共振。
- [ ] 最大尝试次数设了没？没有上限，一次慢故障能拖很久。
- [ ] 重试耗尽后是“转成可读错误”还是“抛给用户”？应该转成消息让 Agent 优雅收尾。
