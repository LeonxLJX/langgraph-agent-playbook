# 案例 03 · 死循环熔断（🟡 中级）

> 一句话：**Agent 卡进死循环疯狂调工具，你要在烧光 token 前把它拽停。**

## 难点是什么
两种典型的“卡死”：
- 反复调用同一个工具（结果一样还继续调）；
- 条件路由在两个节点间来回振荡，永远不落 END。

结果：token 狂烧、请求打到超时、用户等不到答案。

## 为什么会发生
LLM 不是确定性程序。模型在“该不该继续调工具”上判断失误，就可能空转。图本身如果
没设上限，就会一路跑到资源耗尽。

## 生产级解法（看代码 `main.py`）
1. **步数上限**：state 里维护 `steps`，超过 `max_steps` 就注入“强制收尾”提示，逼模型直接作答。
2. **循环检测**：连续 N 次“相同工具调用”（同工具名 + 同参数签名）判定为循环，注入停用提示。
3. **底层兜底**：`recursion_limit` 即使前两招失效也能强制终止。

## 调试清单
- [ ] 有没有 `recursion_limit`？裸图默认是有限深度，但设得太大会拖很久。
- [ ] “相同调用”怎么判定的？比较工具名 + 参数签名，而不是只看消息条数。
- [ ] 熔断后有没有让模型“收尾作答”？只停不答，用户拿不到结果。
- [ ] 正常路径会不会被误伤？阈值别设太小。

## 跑一跑
```bash
python cases/03_loop_guard/main.py --message "帮忙查天气"   # 正常一次就好
pytest cases/03_loop_guard -q                                 # 含故意触发循环的用例
```
想直观感受：把测试里 `loop_threshold` 调到很大、`max_steps` 调小，会看到“步数上限”熔断路径。
